# 开发事项记录

用最少的文档保存跨会话需要的目标、决策、进度和验证。任务记录是历史上下文，当前实现仍以源码、配置和运行结果为准。

中英文请求均按同一语义处理。回复遵循用户明确语言要求及适用语言约定，否则沿用当前对话的主要语言；已有记录保留其语言，新记录按用户要求、项目文档语言或对话语言选择。可翻译模板标题和说明，文件名、任务 ID 和状态值保持不变。

## 按意图选择动作

| 用户意图 | 动作 |
| --- | --- |
| 规划开发事项 / 编排大型需求 / plan development work | 创建或更新计划，不实施代码 |
| 处理 / 实施 / 继续开发事项或大型需求 / implement or resume development work | 复用匹配记录，实施、验证并更新结果 |
| 查看 / 分析 / 校验 / review or check task records | 只读检查，不自动修改记录或代码 |
| 收尾 | 检查验收与实际结果；未完成的如实保留 |
| 迁移旧开发事项 | 按迁移说明整理指定记录；未限定时处理当前仓库全部旧记录 |
| help / 帮助 | 直接说明本表用法，不读取项目文件 |

支持自然语言，不要求记住精确命令。只点名 skill 且意图不明时再询问。创建独立 Codex 任务与创建 `.task` 文档是不同操作。

## 默认一份任务文档

- 单任务保存为 `.task/<slug>/TASK.md`，使用简短 kebab-case 名称；内容参考 [任务模板](assets/templates/task.md)，按实际需要删减。
- 目标、范围、当前状态、验收项和验证结果都在此维护；架构与 API 说明先写在同一文档，确实过长才拆成专项参考。不再创建独立 `PROGRESS.md` 或复制项目规范的 `DEVELOPMENT.md`。
- 状态通常用 `PLANNED`、`IN_PROGRESS`、`BLOCKED`、`DONE`；明确取消可用 `CANCELLED` 并记录原因。状态只维护一处，记录过程用简短日期说明，不重复抄写已完成/待处理清单。
- `.task/README.md` 是可选的链接索引，只在任务较多需要导航时创建；不维护状态、进度或另一套操作规则。
- 共享开发约定只引用项目规范；私有信息按全局与项目约定保存，任务文档只留必要入口。沿用项目对 `.task` 的 Git 策略，被忽略时仍可本地维护，交付时说明未进入提交。

## 工作方式

1. 读取项目规范与明确匹配的任务；可用索引定位，索引不存在就直接查对应路径。普通开发不为发现历史记录而展开全部 `.task`。
2. 结合当前事实校准目标、范围和验收，复用已有任务。用户指定顺序时遵守；只在无法判断目标或存在实质范围变化时询问。
3. 实施时维护当前状态与下一步，记录影响后续接手的决策、阻塞和验证；小步骤合并记录，不逐次工具调用写流水账。
4. 收尾以实际验收为准：逐项关联验证证据；未验证或未完成不能标记 `DONE`，不适用项写清原因。只更新 `TASK.md`；索引链接不变就无需动。
5. 有整体需求时，再维护其集成验收和整体结果。输出记录位置、结果、实际验证方式和必要阻塞；提交仍按用户授权执行。

## 大型需求

只有需要独立验收、明确依赖或分工时才拆子任务，按交付目标拆，不按文件数机械拆。

- 使用 `.task/workflows/<slug>/WORKFLOW.md`，参考 [任务集模板](assets/templates/workflow.md)。这里只维护整体目标、子任务链接与依赖、调度决策和集成验收。
- 子任务状态只在各自 `TASK.md`；依赖只在 `WORKFLOW.md`。不复制状态列、写入范围或批次进度，查看时从源文档汇总。
- 默认在当前任务按依赖顺序实施。启动前检查依赖存在、无环且前置任务已实际完成；规划可以先列未完成的后续任务。
- 整体 `DONE` 需要所有纳入范围的子任务完成、改动集成且整体验证通过；取消的子任务需明确从交付范围移除，不能用取消满足未完成依赖。
- 用户要求并发、独立任务，或需要整理旧记录时，按需读取 [并发与迁移](references/advanced.md)。并发本身不授权创建用户可见的独立 Codex 任务，也不授权 Git 提交或合并。

## 检查原则

校验关注实际问题：依赖缺失/循环、提前执行、写入冲突、任务与事实不符，以及完成状态缺少验收证据。先检查本次涉及的记录；大型复杂依赖可按需用临时脚本核对，不要求所有项目维护固定表格或运行通用格式校验器。
